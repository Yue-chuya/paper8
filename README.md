# Research Paper Replication: AddressSanitizer
## Selected Paper
- **Paper**: AddressSanitizer: A Fast Address Sanity Checker
- **Paper Link**: https://www.usenix.org/system/files/conference/atc12/atc12-final39.pdf
- **Tool**: https://clang.llvm.org/docs/AddressSanitizer.html

## 1. Overview
This repository provides a **reduced-scale reproduction** of selected claims from the selected paper. We use existing Clang/LLVM AddressSanitizer (ASan) instrumentation rather than reimplementing ASan from scratch.

**Purpose:**
The goal is to validate the paper's core claims regarding AddressSanitizer (ASan). Because SPEC CPU2006 is licensed software and was unavailable for us to use, we substitute a GEMM matrix-multiplication workload (`experiments/workload/gemm.c`) and a malloc-intensive workload (`experiments/workload/malloc.c`) to evaluate ASan's functionality and performance trade-offs:

- **Claim 1 Memory-Error Detection**: 
Verifies ASan detection of memory bugs (use-after-free, double-free, heap, stack and global buffer overflow) compiled at `-O0`.

- **Claim 2 Runtime and Memory Overhead**:
Measures execution time and peak memory usage across multiple runs (`-O2` baseline vs. `-O2 -fsanitize=address`), comparing against the paper's reported ~73% slowdown and ~3.37x memory overhead.

- **Extension Experiment**:
Evaluates the impact of redzone size (`128B` vs. `32B`) on runtime slowdown, peak memory overhead, and far out-of-bounds bug detection (`experiments/false_negative/exp_far_oob.c`).

- **Limitations**:
Tests scenarios where ASan may miss bugs (far out-of-bounds beyond redzone, unaligned accesses, and quarantine exhaustion on use-after-free).

## 3. Setup
To reproduce the experiments on a clean machine without hard-coded paths, ensure the following environment and tools are available:

- **Supported Platforms**
    1. Linux (Ubuntu 22.04 on WSL2)
    - Kernel `6.18.54.1-microsoft-standard-WSL2`
    - clang `21.1.8 (6ubuntu1)`
    - GNU Make `4.4.1`, GNU Bash `5.3.9(1)-release`
    - `16 GB` RAM (CPU: 13th Gen Intel(R) / AMD Ryzen 5 4500U)
    
    2. macOS (Apple Silicon) 
    - Kernel `21.6.0 (Darwin)`
    - clang `14.0.0`
    - GNU Make `3.81`, GNU Bash `3.2.57(1)-release`
    - `8 GB` RAM (CPU: Apple M2)

- **Python environment (for plotting)**
    - Python 3 with numpy and matplotlib: `pip install numpy matplotlib`

- **Key Settings Affecting Results**
    - Performance benchmark builds use `-O2` (baseline) and `-O2 -fsanitize=address` (ASan).
    
    - Bug detection and false-negative tests use `-O0 -fsanitize=address -g` to prevent compiler dead-code or undefined-behavior optimizations from removing injected faults prior to instrumentation.
    
    - Paper-parameter runs: `ASAN_OPTIONS="quarantine_size_mb=0:redzone=32:malloc_context_size=0"`

## 4. Build and Run Commands
All commands below assume you are in the repository root directory and use relative paths only.

1. Compile all targets: `make`
2. Run all experiments and generate figures: `make run`
3. Clean up all compiled binaries and temporary logs: `make clean`

## 5. Expected Outputs
- **Raw Logs** `(logs/)`
    - `logs/bug_tests/*.log`: Logs for five memory-error test cases.
    - `logs/extension_bug_tests/*.log`: Far out-of-bounds logs under redzone 32B and 128B.
    - `logs/false_negative/*.log`: Execution logs for three false negative situations.

- **Statistical Results** `(results/)`
    - Containing the per-run raw values, means, standard deviations, slowdowns, and peak memory ratios across 3 runs.

- **Visualizations** `(figure/)`
    - Containing bar charts.

- **Results**   
    - **Benchmark**
        - Slowdown: 68% ~ 75%
        - Memory Ratio: 2.51x
    - **Extension**
        - Slowdown: 24.86% (128B); 20.52% (32B)
        - Memory Ratio: 23.55x (128B); 23.53x (32B)

## 6. Expected Runtimes
-  **Full pipeline (`make run`)**:
`~38 seconds` (The actual runtime varies by CPU and system load).
